Network-panel audit (plan.md §8, constraint 3)

Inspect the service worker's network activity (chrome://extensions → TrueOrigin → “Inspect views: service worker” → Network tab). What appears depends on two caches — the 24 h trust-list cache and the worker's in-memory verdict cache, which lives until Chrome stops the idle worker (~30 s). Observer effect: an open worker inspector pins the worker alive, so the idle teardown separating the tiers never happens while you watch — repeated reloads with the inspector open stay in the warm tier. To reproduce a cold-worker tier: close the worker DevTools, wait for the “Inspect views” line to read (inactive), reopen the inspector (this restarts the worker with an empty verdict cache), then reload this page.

First, one request appears in every tier: the strict-CORS figure's fallback fetch to the cross-host origin (task 5.5), once per analysis, after that figure scrolls into view. Neither cache can skip it — the worker's content-hash cache can only recognize bytes it has already fetched, and the page-view URL cache that would skip the fetch dies with the page. (The worker panel also accumulates entries across page reloads while the inspector is open, so N reloads leave N of these listed.) Beyond that, the tiers differ:

  • Cold worker, cold trust cache (first run in 24 h): five trust-list fetches (verify.contentauthenticity.org ×3, raw.githubusercontent.com ×2) plus the cai-manifests.adobe.com fetch triggered by cloud.jpg. The trust cache persists (Cache API), so a worker restart alone does not return here.
  • Cold worker, warm trust cache (worker restarted via the recipe above, within 24 h): only the cloud.jpg manifest fetch.
  • Warm worker (any reload while the inspector stays open, or within ~30 s of the last analysis): no additional requests — the task-5.2 verdict cache recognizes the image bytes and skips re-analysis, including the manifest fetch.

In every tier, nothing else — no media bytes, no page URLs. The iframe fixtures add nothing to the worker panel: the http(s)-framed images are same-origin to their own frames, so in-frame acquisition succeeds, and the data: frame's opaque-origin instance never escalates to the worker at all (its in-page fetch rides the server's Origin: null carve-out). A fixture URL on the page's own host appearing in the worker panel would be a bug (the fallback firing for a same-origin image). The cross-host fetch itself appears once per analysis attempt: a failed first analysis may legitimately add one retry (the extension allows two attempts per scan cycle, and a source change restarts the cycle) — a steady stream of them is a bug.

In the page's network panel (task 5.2, double-fetch collapse), the pattern is per document: each document — this page and each frame — requests a same-origin fixture URL exactly twice, the render from the network and then the analysis fetch served from (disk cache) / (memory cache), never from the server. The panel aggregates every document in the tab, so a fixture the page and both 480px frames display shows up to six entries in total — audit one document at a time with the DevTools frame selector, or via the server log's host column. Within this page's own document the original counts still hold: the duplicate figure adds no request, and the strict-CORS figure adds its render plus two CORS-blocked analysis attempts (both rungs of the in-page ladder — the counts acquire.test.ts pins). Two frames deviate by design: the tiny frame contributes renders only (its script early-exits before scanning), and the data: frame shows its render, one CORS-blocked force-cache attempt (the render's cache entry carries no ACAO), and the uncredentialed revalidation that succeeds — three entries, two server hits.
